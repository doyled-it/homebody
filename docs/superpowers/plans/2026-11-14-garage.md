# Garage Door Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a garage door module to homebody (trusted status, ntfy alerts, confirmed remote open and close) and a Garage tab on the snaphouse house page.

**Architecture:** A pure `GarageModel` (state, open episodes, injected clock) sits behind a `GarageLink` Protocol, so everything is tested with a fake board and a fake ntfy server. A supervised asyncio task runs the garage next to `Daemon.tick`, sharing nothing with climate except a cheap `occupied()` read and a publish event. The snaphouse PR adds the nginx origin marker, the tab, and the doc fixes.

**Tech Stack:** Python 3.12, uv, pytest, ruff, `aioesphomeapi` (native API), stdlib HTTP for ntfy; snaphouse: Ansible/Jinja2 (nginx), plain ES modules tested with `node --test`.

**Spec:** `docs/superpowers/specs/2026-11-14-garage-design.md` (owner approved 2026-11-14). Read it fully before any task.

## Two PRs, one merge order

| PR | Repo and branch | Tasks |
|---|---|---|
| homebody | `homebody`, branch `garage` (this worktree) | 1 to 7 |
| snaphouse | `snaphouse`, branch `garage-card` (separate worktree, made by the controller) | 8 to 10 |

**Merge and deploy order (the spec requires it):**

1. Merge the snaphouse PR. The Garage tab hides while `garage` is null, so it is inert until homebody ships.
2. Wait for the hub to self-update, then confirm on the hub that `nginx -T` shows the `X-Snaphouse-Origin` map and `snaphouse verify` passes. This is the gate.
3. Merge the homebody PR. The hub self-updates it; the garage stays off until `[garage]` exists in `/etc/homebody/local.toml`.

Homebody treats a missing origin header as `tunnel`, so merging out of order fails safe (home control would be refused) but is wrong. Implementation order is free: Task 8 has no dependencies. Task 10 needs the sample document from Task 5.

## Global Constraints

- No em dashes anywhere: code, comments, copy, docs, commit messages, PR text. Check by counting the character U+2014 with grep (must be 0).
- No identifying data in any repo, test, fixture or log line: no names, emails, IPs, MACs, serials, SSIDs, ntfy topic or token, ESPHome key, board address, or the tunnel hostname. Tests use obviously fake placeholders (`example-topic`, `<key>`).
- The ntfy URL, topic and token, and the board host and noise key, exist only in `/etc/homebody/local.toml`. `local.example.toml` holds generic placeholders.
- Python dependencies are added with `uv add` (`uv.lock` committed; CI uses `uv sync --frozen`).
- A garage failure must never stop climate. Garage code takes no lock shared with climate, never runs inside `Daemon.tick`, writes only `garage.json` and `garage-audit.log`, and never writes `homebody.json` (the daemon is the single writer).
- Nothing moves a door without a person: no automatic close, no retry of a command, no door action from an ntfy button (buttons are `view` links), and no remote command without a fresh single-use nonce. A command is a request for an end state, never a toggle.
- Never show `closed` unless the link is live. `unknown` whenever the link is down or no state has arrived since connect.
- Spec values: ports 6053 (board) and 8783 (API, existing); `X-Snaphouse: 1` guard; nonce 30 s; confirm waits 30 s close, 10 s open (config keys); rate limit 1 command per 10 s and 6 per hour from the tunnel; notification cap 6 per hour (not applied to remote command notes); offline alert after 10 min; reminder at +60 min; audit rotation 256 KB with 2 old files; `recent` holds 10 entries; ntfy retries 3 times over about a minute; status `version` stays 1; settings keys and ranges as in the spec's Settings table (`garage_remote` defaults off).
- Status timestamps are UTC whole seconds (`status.iso`). Every status key is always present, null when unknown.
- Test commands. homebody: `uv run pytest`, `uv run ruff check`, `shellcheck deploy/*.sh` (all green before each PR). snaphouse: `uv run pytest tests/python`, `node --test tests/js`, `ansible-lint`, `ansible-playbook --syntax-check site.yml`.
- TDD: failing test first, watch it fail, then implement. Run the focused test while iterating, the full suite before the last commit of each task.

## Review Focus

Failure modes the spec implies that no obvious test would think of. Each has a test in the task named in brackets.

1. **Reconnect burst.** On connect the board pushes entities one at a time (door before obstruction, or twice). That must not start a second episode, re-fire an alert, or flash `closed` before the door is known. [Task 2]
2. **Wall clock steps backward** (NTP correction, power loss). Durations clamp to zero, nothing fires early, nothing crashes. [Task 2]
3. **Secrets in logs.** Failed ntfy sends and ESPHome auth failures log a status or reason only, never the URL, topic, token, key, board host, or an email. [Tasks 3, 4, 7]
4. **A 30 s close confirm must not block anything else.** While one command waits, a settings POST and the climate tick still complete, and the API's 10 s read timeout does not cut the wait short. [Tasks 5, 6]
5. **Malformed or hostile request bodies.** Wrong types for `action` or `nonce`, a nonce for the other action, a spent nonce, a missing or `home`-looking-but-wrong origin header, and `garage_remote` turned on from the tunnel. [Task 5]

### Task 2: The garage model (pure state, episodes, persistence)

**Files:**

**Interfaces:**
- Consumes: `LinkState` (Task 1).
- Produces (`garage.py`):
  - `DoorState = Literal["closed","open","opening","closing","stopped","unknown"]`
  - `@dataclass(frozen=True) class GarageSettings: left_open_minutes: int = 15; away_open_grace_minutes: int = 5; alerts: bool = True; remote: bool = False`
  - `@dataclass class Episode: started: float; fired: set[str]; remote_started: bool = False; since_approximate: bool = False`
  - `class GarageModel(clock: Callable[[], float], saved: dict | None = None)` with `link_changed(connected: bool) -> None`, `state_received(link: LinkState) -> None` (returns nothing; read results from properties), properties `state: DoorState`, `since: float | None`, `since_approximate: bool`, `last_seen: float | None`, `connected: bool`, `episode: Episode | None`, `obstruction`, `lockout`, `light`, `position_percent: int | None`, `last_known_state: DoorState | None`; `note_remote_command() -> None` (marks the current or next episode `remote_started`); `to_saved() -> dict`; `changes: list[tuple[float, DoorState]]` drained by `pop_changes()`.
  - `class GarageStore(directory: Path)` with `load() -> dict` (missing or damaged returns `{}`), `save(data: dict) -> None` (write temp, fsync, `os.replace`, file `garage.json`). It does not import or reuse `daemon.StateStore`, on purpose (isolation).

Rules to implement (spec "State model and transitions"): operation `opening` or `closing` wins; otherwise position 0 is `closed`, 1 is `open`, and an in-between resting position is `stopped` only when `has_position` (binary shape treats it as `open`). `unknown` while disconnected or before the first push since connect, and the model never carries a door state across a drop. An episode starts when the door leaves `closed`, ends at `closed`, and `unknown` neither starts nor ends one. On the first push after connect: if it equals the saved state keep the saved `since`, else `since` is the connect time and `since_approximate` is true. A saved open episode survives a restart only if the board still reports non-closed; otherwise a fresh episode starts at connect time with `since_approximate` true.

Behavior (spec "Command semantics", "Security"): nonce is single use, bound to its action, in memory, expires in 30 s. Order of checks in `command`: nonce (400, "That request expired. Start again."; the spec gives no code for this, see spec gaps), tunnel needs `settings().remote` (403), tunnel needs ntfy configured (409, clear sentence), state `unknown` (503 when the link is down, 409 otherwise), lockout (423), `close` with obstruction (409; `open` with obstruction is allowed), end state already reached (200 no-op, no rate-limit charge), door moving the other way (409), rate limit 1 per 10 s overall and 6 per hour from the tunnel (429). For a tunnel command the note ("Garage open requested from away") is started first and the send waits for it or `note_wait`, whichever is first; a failed note still lets the command through and audits "note failed". After `link.send`, wait for the model to report `opening` or `closing` (30 s close, 10 s open); no sight of movement raises 504 with "No movement seen yet. Check the card before trying again."; a movement within 60 s after a 504 is audited "late confirm". Never retry. A board refusal (`LinkError`) raises 503 and sends a second note line for tunnel commands.

Plan decision: encryption required unless `allow_plaintext = true` is set explicitly (builder's call recorded in Task 5); the owner should know the board needs a key added.
3. **API handler is synchronous with a 10 s timeout.** The spec's 30 s close wait cannot run inside `api.handle` and `READ_TIMEOUT_SECONDS`. Plan adds an async garage path with its own 45 s timeout (Tasks 5 and 6).
4. **nginx `geo`/`map` cannot live in `homebody.conf`.** That file is included inside the `server` block. Plan adds an http-level file in `conf.d` (Task 8).
5. **IPv6 LAN requests.** The spec's `geo` lists only IPv4 private ranges, so an at-home IPv6 request would be `tunnel` (confirm step plus a missing Access header means commands refused at home). Plan adds `fc00::/7` and `fe80::/10`. Owner-level check: confirm the LAN uses these, not global IPv6.
6. **Nonce failure code.** The spec's error list has no code for a bad, spent or expired nonce. Plan uses 400 with "That request expired. Start again."
7. **Cross-repo sample.** "Snaphouse's contract test reads a sample from homebody's tests" cannot work in two separate CIs. Plan keeps a byte copy in snaphouse and a homebody test that builds the document from the real code and compares it with the sample, so drift fails in homebody first.
8. **Loopback noise server.** The spec asks the loopback server to speak plaintext and noise. Plan covers plaintext end to end and asserts the key reaches the client; the noise handshake is left to the library and install day.
9. **`aioesphomeapi` version.** `uv add` resolves 44.19.0 because of the matter-server pin on `zeroconf`, not the latest 46.x. Fine for v1, worth knowing.
10. **Approval-only notes, not blockers.** The spec's `since_approximate` wording, alert text, and the `open`-with-obstruction rule are left to the builder as the spec says (plan allows open).
